# memex 기억 인출 데이터 기획

상태: 구현 전 제품·데이터 설계 초안. 현재 구현과 제안 필드를 구분한다.
기준일: 2026-09-13.
연결: [노트 작성 UX](2026-09-13-note-authoring-ux-plan.md), [연구 조사](../research/2026-09-13-human-memory-filesystem-research.md).

## 1. 목표

사용자가 일부 단서만 주어도 관련 원문을 찾고, 프로젝트의 현재 결정과 변화 과정 또는 글쓰기에 쓸 생각·근거를 재구성한다. 각 결과는 출처를 확인하고 현재 작업에 사용할 수 있어야 한다.

대표 질문:

- “memex 제품 방향 어디까지 정했지?”
- “노트 앱 쪽으로 바꾸기 전에 왜 반대했더라?”
- “기억에 관한 글을 쓰려는데, 예전에 내가 겪은 사례와 반대 의견을 찾아줘.”
- “그 회의에서 민수님이 말했던 우려가 뭐였지?”

인물과 회의는 예시이며 실제 인물 관계를 가정하지 않는다. 목표는 뇌의 복제나 모든 활동의 기록이 아니라, 이 질문들에 필요한 단서와 근거를 충분히 보존하는 것이다.

## 2. 현재 구현의 재사용 범위

| 현재 자산 | 실제 역할 | 보완할 지점 |
|---|---|---|
| notes, document_meta, revisions | 파일·작성 출처·수정 이력 | 필드별 시간/출처 의미를 유지하며 작업 맥락 연결 |
| chunks + FTS + vectors + note_links | 구절 검색과 한 단계 링크 확장 | 목적별 검색, 사건·시간·관계 확장 |
| claims, register, amendments, evidence | 주장 상태·현재 값·정정·근거 변화 | 기존 의미를 보존하는 공통 조회, 시간 질문과 연결 |
| document_references | 문서별 원본 revision과 인용 | 같은 문서의 복수 구절·관계 종류·사용 작업 |
| change_proposals.used_evidence | AI 변경 제안의 사용 근거 | 인출 실행과 실제 적용 결과 연결 |
| retrieval_log | 검색 결과 노출·주입 | 검색 실패, 세션/목적, 실제 사용 결과와 구분 |
| chat_sessions / chat_turns | 앱 대화 기록 | 문서·인출 실행·선택 근거의 연결 |
| ContextManifest | 문서·선택 영역·참고·지침·검색 범위 | 공통 검색 계약에 작업 맥락 전달 |

근거: `packages/db/src/{schema,document-meta,document-references,retrieval-log,claims,register,repository,migrations}.ts`, `apps/cli/src/services/chat/context.ts`, `packages/core/src/note.ts`.

새 데이터는 기존 구조를 확장하거나 연결한다. 또 하나의 병렬 claim DB나 독립적인 저장 서비스를 만들지 않는다. 아래 명칭은 논리적 개념이며 모두 별도 테이블을 만들라는 지시가 아니다.

## 3. 인출에 필요한 데이터

| 데이터 | 최소 필드 | 얻는 시점/방법 | 해결하는 질문 | 단계 |
|---|---|---|---|---|
| 원본과 버전 | documentId, revisionId, sourceUri, origin | 기존 저장·색인·가져오기 | “무엇을 근거로 하나?” | 기존 재사용 |
| 구절 anchor | revisionId, exactQuote, headingPath, from/to, 주변 구절 | 검색·인용·AI 근거 생성 | “원문 어디에 있나?” | 1 |
| 시간 의미 | authoredAt, recordedAt, occurredAt 또는 범위, 시간대·정밀도·출처 | 앞의 둘은 시스템, 사건일은 명시 문장/사용자 지정 우선 | “그때 무슨 일이 있었나?” | 1, 추출은 2 |
| 작업 맥락 | workId, targetDocumentId, 목적, 선택 자료, 시작/마지막 활동 | 문서 작업 진입·명시적 작업 연결 | “어디까지 했지?” | 1 |
| 인출 요청 | query, intent, target/selection, scope, asOf, 언어·사용자 단서 | 검색/AI 요청 snapshot | “이번에는 무엇을 찾나?” | 1 |
| 결과와 출처 | runId, 후보 ID/anchor, 순위·회수 경로, 선택 근거, 제외 이유 | 검색·재구성 실행 | “왜 이 기록이 나왔나?” | 1 |
| 실제 사용 | runId/workId, documentId/revision, action, at, actor | 원문 열기·참고 추가·인용·AI 제안 적용 | “무엇이 도움이 되었나?” | 1 |
| 사람·프로젝트 | entityId, kind, 이름·별칭, evidenceAnchor, 상태 | 명시 연결 먼저, 본문 추출은 제안 | “누구와 어떤 일에서?” | 2 |
| 사건 묶음 | episodeId, 기간, 관련 자료·사람·프로젝트, 근거, 생성 방식 | 대화/문서의 명시 관계 + 검토 가능한 추출 | “한 사건을 여러 기록에서 복원” | 2 |
| 의미 관계 | source/target, relation, evidenceAnchor, origin/status | 인용·정정 등 확실한 동작 먼저 | “왜 바뀌었지?” | 1/2 |
| 재구성 결과 | runId, 목적, statements와 근거, unresolved, sourceRevisions, generatedAt | 인출 후 합성 | “지금 믿고 쓸 맥락은?” | 1 |

분류되지 않은 자료와 시간이 불명확한 기록도 검색 대상이다. 메타데이터가 없는 기록을 조용히 버리지 않는다.

## 4. 시간과 출처 계약

네 시간을 섞지 않는다.

- 기록 시각(recordedAt): memex에 들어온 때. 기존 createdAt 의미를 바꾸지 않는다.
- 작성 시각(authoredAt): 원문이 쓰인 때. 근거가 없으면 unknown.
- 사건 시각(occurredAt): 본문이 말하는 일이 생긴 때. 범위·대략적 월·unknown 허용.
- 사실의 유효기간(validFrom/validUntil): 해당 주장이 적용되는 기간. 기존 claims/register를 재사용하며 기록일에서 추정한 값과 명시된 사실 기간을 구분한다.

updatedAt은 파일 수정 시각이다. 제목이나 태그를 바꿨다고 사실이 새로 확인됐다고 판단하지 않는다. “현재” 질문에서는 유효기간·대체 관계·확인 상태를 우선하고 수정일은 보조로만 사용한다. “과거” 질문에서는 당시 유효했던 주장과 이후 정정을 함께 표시한다.

추출 필드는 explicit / inferred / unknown과 근거를 가진다. modelConfidence는 사실의 확률로 표시하지 않는다. 사람의 확인 여부, 출처 작성자, AI 추출 여부는 별개 속성이다. 사람이 AI 초안 전체를 적용해도 모든 문장을 확인된 사실로 바꾸지 않는다.

## 5. 작업과 참조의 최소 모델

workId는 회의나 프로젝트 자체와 같지 않다. 문서 기반으로 이어가는 작업의 식별자다. 기본은 열린 문서를 작업 기준으로 삼고, 여러 문서를 묶는 것은 사용자의 명시 선택으로 시작한다. 폴더가 같다는 이유나 30분 안에 열었다는 이유만으로 같은 작업이라고 확정하지 않는다.

작업에는 목표 문서, 선택 자료, 마지막 확인된 위치, 최신 인출 실행과 결과를 연결한다. 앱 대화의 chatSessionId와 외부 MCP가 제공한 대화 ID는 선택적 연결이다. 외부 클라이언트가 ID를 주지 않으면 unknown으로 남기고 대화 경계를 지어내지 않는다. 장시간 비활성은 방문 구간을 나눌 수 있지만 같은 작업의 정체성을 바꾸지는 않는다.

참조에는 여러 구절을 허용한다. 현재 `(owner_document_id, source_document_id)` 유일성으로는 같은 자료의 여러 인용이 하나로 갱신되므로, 문서 간 연결과 구절 evidence를 분리하거나 유일성 범위를 변경해야 한다. 기존 참조 ID와 링크는 마이그레이션으로 유지한다.

anchor는 문서 ID만이 아니라 revision과 인용 구절을 가진다. 새 revision에서 정확히 대응되면 current, 변경되면 changed, 없어지면 missing, 여러 곳이 일치하면 ambiguous다. 같은 문구가 반복된다고 첫 위치에 임의로 재연결하지 않는다. 과거 원문은 기존 revision 저장소에서 연다.

관계 최소 어휘:

| 관계 | 생성 권한과 의미 |
|---|---|
| references / quoted_from | 사용자의 참고 추가·인용 동작에서 생성 |
| continues | 명시적 후속 기록 또는 AI 제안임을 표시 |
| corrects / supersedes | 기존 정정·대체 계약으로만 확정 |
| supports / contradicts | 근거 구절을 가진 검토 가능한 추출, 사람 확인과 구분 |
| considered_because / decided_because | 이유가 원문에 명시됐을 때 추출 가능, 시간 순서만으로 만들지 않음 |

## 6. 수집 원칙과 이벤트

기존 저장 revision, 참고 자료, 제안 적용 경로에서 이벤트를 남긴다. 매 키 입력, 전체 클립보드, 화면 감시, OS 전역 활동 기록은 이 기능에 필요하지 않다. 미저장 선택 텍스트는 요청 처리 맥락으로만 쓰고 별도 원문 아카이브로 축적하지 않는다.

| 이벤트 | 해석 | 해석하면 안 되는 것 |
|---|---|---|
| result_shown | 후보가 화면 또는 모델 입력에 제공됨 | 사용자가 읽거나 동의함 |
| source_opened | 원문을 열었음 | 유용했음 또는 사실 확인 |
| reference_added | 이번 문서의 참고로 선택함 | 그 자료의 모든 주장이 참 |
| passage_quoted | 해당 구절을 사용함 | 인용 내용에 동의함 |
| proposal_applied | 변경안을 적용함 | 사용 근거 전체를 사실 승인 |
| result_dismissed | 이번 요청에서 제외함 | 원문이 틀렸거나 영구적으로 불필요 |
| correction_committed | 특정 주장에 명시적 정정이 적용됨 | 같은 문서 전체 폐기 |

이벤트는 idempotency key, actor, workId/runId, 문서/구절, 시각을 가진다. adapter가 사람/agent 출처를 정하며 요청 payload만으로 사람 행동을 위조할 수 없게 한다. 재렌더·재시도·포커스 흔들림은 반복 사용으로 집계하지 않는다. 검색 결과 0건과 실패도 run 단위로 기록한다. 현재 retrieval_log는 결과가 없으면 쓰지 않으므로 이 계측은 확장이 필요하다.

제안 보존 정책: 진단성 노출/열람 로그 30일, 저장된 작업·인용·결정 근거는 연결 문서 수명에 맞춰 유지. 사용자가 기록을 지우거나 수집을 끌 수 있고 기존 문서 검색은 작동한다. 파생 색인을 지우면 재생성할 수 있지만 사용자 선택 trail은 백업 대상이다. 문서 영구 삭제 시 해당 파생 텍스트·캐시도 제거하고, 공유 결과에는 접근 불가 출처의 내용을 남기지 않는다.

## 7. 인출 처리 흐름

1. 요청 해석: explicit mode가 있으면 우선한다. 그 외에는 lookup / resume / history / explore를 추정하되 사용자에게 보이는 렌즈로 둔다. 목적을 못 정하면 일반 검색으로 시작한다.
2. 범위 확정: 사용자 선택 자료와 허용 볼트. 앱의 selected / allowed-vault 계약을 유지한다. 현재 문서의 raw 개인 내용은 사용자 입력 없이 외부 검색으로 보내지 않는다.
3. 후보 회수: 기존 FTS·벡터·제목·태그에 문서/작업·기간·명시 엔티티 단서를 추가한다. 일부 조건은 soft hint이며 명시 필터만 hard constraint다.
4. 관계 확장: resume/history는 후속·정정·이유 근거를, explore는 관련 관점과 반대 근거를 추가한다. 최대 2 hop·30문서에서 시작하고 실측으로 조정한다. 한도를 넘으면 빠진 범위가 있음을 응답에 남긴다.
5. 상태 판별: 수정일로 현재성을 결정하지 않는다. 기존 register/claims와 근거 revision을 조회하고 충돌·불확실성을 유지한다. 오래된 생각도 history/explore에서는 유효한 결과다.
6. 근거 선택: 중복을 줄이되 핵심 구절과 정정 근거를 우선 포함한다. 문서 앞부분을 일괄 자르는 방식 대신 anchor와 주변 문맥을 예산 내에서 선택한다.
7. 재구성: 현재 결정 / 결정 이유 / 변경 / 미결 질문 또는 관련 생각 / 사례 / 반대 관점으로 구성한다. 각 진술에 근거를 연결하고 원문에 없는 이유는 unknown으로 둔다.
8. 작업 연결: 참고 추가·인용·새 노트·AI 수정 제안으로 결과를 사용한다. 선택과 결과를 workId/runId로 남겨 다음 재진입에 사용한다.

AI/임베딩을 사용할 수 없으면 키워드 검색·명시 링크·시간 필터·저장된 참고 자료로 접근한다. 이전 요약은 생성 시점과 근거 변경을 표시한다. 재구성 실패를 검색 결과 없음으로 바꾸지 않는다.

## 8. 동일한 결과 계약

앱과 MCP는 공통 인출 서비스의 같은 결과를 사용한다. 새 최상위 CLI 명령을 추가하지 않는다. MCP도 별도 중복 읽기 도구를 늘리기 전에 기존 search/get 계약의 선택 인자로 확장한다.

```text
RetrievalRequest
  query, intent?, workId?, targetDocumentId?, selection?, referenceIds?
  scope, timeHint?, entityHints?, asOf?, budget?

RetrievalResult
  runId, resolvedIntent, effectiveScope, sources[]
  statements[{text, kind, evidenceAnchors[], epistemicStatus}]
  conflicts[], unknowns[], omitted[], sourceRevisions[], generatedAt
```

scope는 검색 힌트가 아니라 읽기 허용 경계다. 저장된 결과를 재사용할 때도 권한과 최신 revision을 재확인한다. 사용 가능한 근거가 없으면 답을 보류한다. 검색어·목적·scope·근거 revision 집합·생성기 버전이 바뀌면 요약 캐시를 그대로 재사용하지 않는다.

## 9. 화면에 드러나는 경험

문서 오른쪽 “참고” 패널에 검색과 “이어서 보기”를 둔다. 사용자가 문서 작업을 시작할 때 전역 기억 점검을 먼저 요구하지 않는다.

예시 결과:

```text
memex 제품 방향 · 이어서 보기

지금 기준
  직접 쓰기와 기억 인출을 함께 개선한다.                  [근거 2]
이전과 달라진 점
  교정 중심 앱에서 직접 작성하는 작업 공간으로 방향이 바뀌었다. [변경 보기]
남은 질문
  노트 작성에서 가장 먼저 해결할 불편은 무엇인가?         [원문]

[참고에 추가] [이 내용으로 노트 작성]
```

이 예시는 대화 맥락을 설명하기 위한 기획용 표현이다. 실제 제품은 존재하는 source ID와 revision 없이 근거 버튼을 만들지 않는다. 사람·기간 필터는 사용자가 제공한 단서와 근거가 있을 때 제안한다.

## 10. 단계별 구현

### 1차: 기존 데이터로 인출을 완결한다

작성 UX의 문서 저장·참고 추가와 함께 work/run/evidence 연결을 구현한다. 기존 claims/register/amendments를 공통 인출 서비스에서 조회한다. resume/history/explore, 근거 링크, 충돌/unknown, 결과 사용 이벤트를 완결한다. 엔티티 자동 추출이나 별도 그래프 DB는 선행 조건이 아니다.

통과: 기존 한국어 기록으로 “어디까지 했지?”와 “왜 바뀌었지?”에 출처가 있는 답을 만들고, 참고에 추가한 뒤 재실행해 같은 작업을 이어간다.

### 2차: 부분 단서를 확장한다

사람·프로젝트 별칭, 사건 시각, 사건 묶음, 관계의 근거를 추가한다. 명시 연결을 우선하고 AI 제안은 추정 상태로 둔다. 동명이인·중복 프로젝트명을 자동 병합하지 않는다. 사용자는 잘못 연결된 관계만 해당 위치에서 고칠 수 있다.

통과: 정확한 파일명 없이 사람·시기·당시 작업으로 찾고, 잘못 연결된 엔티티를 분리해도 원문과 과거 인용을 잃지 않는다.

### 3차: 사용 경험으로 개선한다

실제 사용 이벤트를 현재 작업 범위의 재진입·랭킹 개선에 활용한다. 자주 노출된 AI 요약이 자기 자신을 강화하지 않도록 사람의 선택과 모델 노출을 분리한다. 빈도는 진실 판정에 사용하지 않는다. 기준 검색 대비 이점이 있을 때만 적응 랭킹을 활성화한다.

## 11. 검증 계획

현재 검색을 baseline으로 고정하고 같은 볼트 snapshot·질의·모델·예산에서 비교한다. 가능하면 사용자의 실제 재사용 질문으로 30문항을 만들고, 합성 예시는 별도 표시한다. expected evidence는 사용자 확인이나 명시된 원문으로 만들며 모델 생성 정답만으로 평가하지 않는다.

| 과업 | 제안 문항 수 | 확인 내용 |
|---|---:|---|
| 정확/부분 단서 검색 | 6 | 제목을 몰라도 기대 원문 회수 |
| 프로젝트 이어가기 | 6 | 현재 결정·이유·미결 질문의 근거 |
| 시간/변경 질문 | 6 | 과거와 현재 구분, 정정 누락 |
| 글감/여러 관점 | 6 | 서로 다른 자료의 재사용 가능성, 반대 관점 |
| 부재/충돌/접근 제한 | 6 | 모름·충돌 표시, 범위 밖 자료 미사용 |

측정: evidence recall@10, 근거 연결 정확성, unsupported statement 비율, 현재성 오류, 사용자 작업 완료 시간, 실제 인용/참고 추가, p50/p95 지연과 모델 비용. “추천된 문서 수”나 “AI 주입 횟수”를 성공으로 세지 않는다.

제안 출시 게이트: 접근 경계 위반·원문 손실 0건, 생성 진술마다 근거 또는 unknown 표시, 시간/정정 필수 fixture 전부 통과, 기존 검색 대비 근거 recall 저하 없음. 실제 작업 시간 개선과 초기 수치 목표는 baseline 측정 후 확정한다. 30문항 통과를 일반적인 기억 정확도 보장으로 표현하지 않는다.

필수 예외: 같은 문구 반복, 동일 인물명, 사건일/작성일 차이, 제목만 수정, 참고 원문 수정/삭제, 일부 주장만 정정, AI 원문 오독, 과거 주장 검색, 빈 검색, 긴 자료 예산 초과, 다른 문서로 탭 이동, MCP 동시 수정.

## 12. 마이그레이션과 구현 경계

- 새 필드는 nullable/unknown 기본값. 과거 데이터를 근거 없이 보충하지 않는다.
- 기존 ID·Markdown·revision·MCP 호출을 보존하는 additive migration. legacy field의 시간 의미 변경은 별도 migration과 테스트가 필요하다.
- 원본 parsing/관계 검증/목적별 선택은 순수 모듈, 수집·생성·저장은 services, 데이터 접근은 db, 프레젠테이션은 ui로 분리한다.
- 새 도메인 서비스는 노트 작성·검색·회수·정정이 같은 계약을 쓰게 한다. UI event나 SQL row를 도메인 API에 그대로 노출하지 않는다.
- fixture 볼트와 백업/복구 검증 후 적용한다. 사용자 규칙 #2280은 이번 문서 작성으로 자동 폐기하거나 승인하지 않는다.

## 13. 기획 판단과 연구의 관계

시간·사람 단서와 기억 실패를 고려한 재검색은 [Stuff I’ve Seen](https://www.microsoft.com/en-us/research/publication/stuff-ive-seen-a-system-for-personal-information-retrieval-and-re-use/) 및 [Towards Memory Supporting PIM Tools](https://strathprints.strath.ac.uk/2395/)를 참고했다. 위 work/run/anchor 모델, 보존 기간, 탐색 한도는 memex를 위한 설계 제안이며 해당 논문이 직접 검증한 수치가 아니다. 앞선 연구 문서 전체의 개별 서지·일반화 주장은 구현 근거로 사용할 때 원문을 추가 확인한다.
