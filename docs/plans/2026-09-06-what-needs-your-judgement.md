# 검토 큐 — 정보 구조와 상태 전이

> 운영 계약 memex #2280 §3-3의 승인 요청서. 코드는 건드리지 않았다.
> `2026-09-04-home-review-session.md`가 홈의 위계를 정했고, 이 문서는 **1단계 안쪽**을 정한다 —
> 무엇이 검토 항목이 되고, 항목 하나가 어떤 상태를 지나며, 네 가지 행동이 각각 무엇을 바꾸는가.
>
> 제품 정의는 그대로다. **memex는 AI의 기억을 구경하는 앱이 아니라 사람이 감독하는 앱이다.**
> 아래 어떤 항목도 "읽을거리"로 설계하지 않았다.

## 1. 검토와 활동을 가르는 두 개의 게이트

지금 `apps/cli/src/services/ui/today.ts`의 `shareOut`은 세 종류를 라운드로빈으로 섞는다.
`evidence-moved`(AI가 틀리게 알고 있을 수 있음), `typo-link`(볼트에 오타 링크가 있음),
`undeclared`(노트에 출처 메타데이터가 없음). 앞의 하나만 기억 감독이고 뒤의 둘은 파일 정리다.
섞으면 사용자는 자기가 무엇을 하는 중인지 모른다.

항목이 **검토(1단계)**에 들어오려면 두 질문에 모두 예여야 한다.

| 게이트 | 질문 | 아니면 |
|---|---|---|
| **영향** | 이걸 그대로 두면 AI가 다음 대화에서 다르게 행동하는가 | 활동 기록(2단계)이거나 볼트 정리(3단계) |
| **독점** | 볼트 밖에만 있는 정보라서 사람만 답할 수 있는가 | 볼트 정리 — 사람의 큐가 아니라 자동화 대상 |

여기에 계약 §정보 구조 원칙에서 온 세 번째 조건이 붙는다.

| **답변 가능** | 카드가 요구하는 네 답을 **결정론적으로** 들고 있는가 | 3단계. 추측으로 카드를 채우지 않는다 |

세 번째가 `stale_state` 신호 30건을 1단계에서 떨어뜨린다. "근처에 노트 3개가 쌓였다"는
임계값 휴리스틱이지 무엇이 어떻게 틀렸다는 관측이 아니다.

### 지금 있는 항목들의 배치

| 지금 있는 것 | 개수(2026-09-04 실측) | 어디로 | 왜 |
|---|---:|---|---|
| 낡은 추론 (`inferences.status='stale'`) | 9 | **1단계 검토** | 근거 본문 해시가 실제로 어긋났고, 어느 근거인지 이름까지 있다 |
| 근거가 정정된 state (`note_evidence` → `amendedBy`) | 4 | **1단계 검토** | 이 판단이 딛고 선 기록이 뒤집혔다 |
| 승인 대기 rule (`rule_status='provisional'`) | 0 | **1단계 검토** | 승인 즉시 미래 행동을 바꾼다. 가장 직접적이다 |
| 믿음 충돌 (`signals.type='conflict_candidate'`) | 0 | **1단계 검토** | 두 값이 동시에 참일 수 없고 어느 쪽인지는 사람만 안다 |
| 근거가 사라진 판단 (source 노트 missing) | — | **1단계 검토** | 결론을 꾸며내지 않고 `근거 부족`으로 표시한다 |
| 낡았을 수 있는 state (`stale_state`) | 30 | 3단계 | 추측이다. 무엇이 틀렸는지 말하지 못한다 |
| 끊긴 링크 · 오타 링크 | 128 | 3단계 | 믿음 변화가 아니다. 가장 가까운 제목을 기계가 안다 |
| 출처 미선언 state (`undeclared`) | 30+ | 3단계 | 쓰기 시점 문제다. MCP 규약이 `derives_from`을 이미 요구한다 |
| 태그 병합 · 외톨이 태그 | — | 3단계 | 파일 정리다 |

**1단계에서 빠진 것들은 사라지지 않는다.** 3단계 `볼트 상태`로 내려가고, 거기서
"기억이 아니라 파일에 대한 일"로 묶인다. 상시 카운터로 노출하지 않는 것은 그대로다.

## 2. 검토 항목 다섯 종류

각 종류가 무엇을 근거로 감지되는지, 그리고 카드의 네 칸을 무엇으로 채우는지.

| 종류 | 감지 (결정론적) | AI는 이렇게 알고 있어요 | 무엇이 바뀌었나 | 근거 |
|---|---|---|---|---|
| `rule-proposal` | `layer='rule' AND rule_status='provisional'` | 규칙 한 줄 | (변화 아님 — 신규 제안) | 규칙이 인용한 근거 노트 |
| `belief-conflict` | `signals.type='conflict_candidate'` | 양쪽 주장 두 줄 | 나중 노트가 앞 노트와 어긋남 | 충돌하는 두 노트 원문 |
| `evidence-corrected` | `note_evidence.source_id`를 `amends_kind='corrects'`가 겨냥 | state 노트의 주장 | 근거 노트의 어느 문장이 `invalidates`로 뒤집혔나 | 원본 문장 · 정정 문장 · 정정 노트 |
| `evidence-moved` | `inference_evidence.source_hash ≠ 현재 bodyHash` | 추론의 요약 한 줄 | 근거 노트 본문의 이전/현재 (git 리비전) | 발췌(`source_excerpt`) · 현재 본문 |
| `evidence-missing` | source 노트가 없음 (FK 캐스케이드 없음) | 판단의 요약 한 줄 | 근거가 사라짐 | 마지막으로 알던 경로와 발췌 |

`evidence-moved`의 "이전 값"은 `inference_evidence.source_excerpt`와 볼트의 git 히스토리에서
나온다. `apps/cli/src/services/ui/history.ts`가 이미 `git log`와 리비전을 읽으므로 재료는 있다.
`note_changes`는 종류만 들고 값은 없다 — 여기에 기대지 않는다.

## 3. 카드 — 네 개의 답과 3단 공개

계약이 지정한 네 질문은 그대로다. 바뀌는 것은 **한 화면에 얼마나 펴는가**다.

```
┌──────────────────────────────────────────────────────────────┐
│  지금 확인할 것                                   2 / 5      │
│                                                              │
│  ┌────────────────────────────────────────────────────────┐  │
│  │ 근거가 정정됐어요                        관측 · 재발     │  │  ← 종류 · 출처등급
│  │                                                        │  │
│  │ AI는 이렇게 알고 있어요                                  │  │
│  │   "Opula의 트라이얼은 14일이다"                          │  │
│  │   「Opula 유료화 전략 v2」 · state · 9월 1일             │  │
│  │                                                        │  │
│  │ 무엇이 바뀌었나                                          │  │
│  │   이 판단이 딛고 선 「Opula 가격 결정」의 한 문장이        │  │
│  │   9월 2일 정정됐어요                                     │  │
│  │     이전  트라이얼은 14일로 한다                          │  │
│  │     현재  트라이얼은 7일로 줄인다                         │  │
│  │                                                        │  │
│  │ 그대로 두면                                             │  │
│  │   가격을 묻는 대화에서 14일이 계속 쓰여요                  │  │
│  │   지난 30일 동안 이 노트가 3번 주입됐어요                 │  │
│  │                                                        │  │
│  │ [ 맞아요 ]   [ 고칠게요 ]   [ 나중에 ]                   │  │
│  │                                                        │  │
│  │ 근거 3건 보기 ▾                         이 기억 지우기   │  │
│  └────────────────────────────────────────────────────────┘  │
│                                                              │
│  ▪ 승인 대기 규칙 1건    ▪ 낡은 추론 2건       ← 접힌 나머지   │
└──────────────────────────────────────────────────────────────┘
```

**3단 공개.**

| 단 | 무엇 | 언제 |
|---|---|---|
| 1 | 위 카드 — 네 답과 이전/현재 한 쌍 | 항상 |
| 2 | `근거 n건 보기` — 근거 노트 목록, 각각 배지(`그대로` · `바뀜` · `정정됨` · `사라짐`) | 펼칠 때 |
| 3 | 원문 노트 화면 | `고칠게요`를 누르거나 근거를 클릭할 때 |

**한 번에 한 장만 편다.** 나머지는 아래 접힌 줄로만 존재하고, 처리하면 다음 장이 열린다.
다섯 장을 동시에 펴면 그건 백로그다.

`지난 30일 동안 3번 주입됐어요`는 `retrieval_log`의 `injected` 컬럼에서 나온다.
사용된 적 없는 기억과 매주 쓰이는 기억은 같은 위험이 아니고, 그 차이가 우선순위를 정한다.

## 4. 네 가지 행동 — 종류마다 다른 것을 의미한다

**승인·수정·보류가 주 행동이고 삭제는 같은 급이 아니다.** 셋은 되돌릴 수 있고 삭제는 아니다.
그래서 삭제는 카드 아래쪽의 부차 위치에 놓고, 라벨도 종류마다 다르게 쓴다 —
`rule` 제안을 거절하는 것과 `state` 노트를 지우는 것은 같은 일이 아니기 때문이다.

| 종류 | 맞아요 (승인) | 고칠게요 (수정) | 지우기 (삭제) | 나중에 (보류) |
|---|---|---|---|---|
| `rule-proposal` | `rule_status='canonical'`. 다음 세션부터 `## House Rules`에 주입된다 | 규칙 문안을 편집한 뒤 승인 | **거절** — `declineRule`. rule이 아니라 `past`/`state`로 내려가고 내용은 남는다 | 제안 상태 유지. 주입되지 않는다 |
| `belief-conflict` | 어느 쪽이 참인지 고른다. 진 쪽에 `invalidates`가 기록된다 | 두 쪽 다 틀렸다 — 노트 화면에서 정정 노트를 쓴다 | 신호를 `dismissed`. 충돌이 아니라고 판정한 것 | 신호 `snoozed` |
| `evidence-corrected` | 근거가 바뀌어도 이 주장은 유효하다 → `confirmedAt` 갱신 + `note_evidence` 재선언 | 노트 화면으로. 주장을 고치고 저장하면 재선언 | **철회** — state 노트 삭제. 파일 삭제이므로 한 단계 확인 | 아래 §6의 깨어날 조건과 함께 |
| `evidence-moved` | `reviveInference` → `active`. 근거 해시 재선언 | 추론 요약 편집 후 재선언 | `status='archived'`. 테이블에 남되 어디서도 읽히지 않는다 | 상동 |
| `evidence-missing` | 승인 불가 — **근거 없이 승인시키지 않는다** | 근거를 다시 연결하거나 판단을 고친다 | 아카이브 / 철회 | 상동 |

세 가지 규율이 이 표를 관통한다.

- **`past`는 지우지 않는다.** 무슨 일이 있었는지의 기록은 불변이고, 틀렸으면 `amends`로 정정한다.
  삭제 가능한 것은 투영(`state`), 가설(`inference`), 제안(`rule`)뿐이다.
- **거절은 파기가 아니다.** `declineRule`이 이미 그렇게 되어 있다 — 규칙이 아니었다고 말하는 것이지
  에이전트가 관찰한 것을 버리는 게 아니다. 삭제 UI 전체가 이 의미론을 따른다.
- **근거가 없으면 승인 버튼이 없다.** `evidence-missing`에서 승인을 허용하면 앱이 사람에게
  근거 없는 서명을 시키는 것이 된다. 그 자리에는 `[ 근거 다시 연결 ]`과 `[ 나중에 ]`만 둔다.

**수정은 홈에서 하지 않는다.** 계약대로 해당 노트·주장·근거의 맥락에서 한다. 다만 세션 문맥을
들고 이동하고, 저장하면 검토 세션으로 돌아와 다음 장이 열린다. 별도 관리 화면을 만들지 않는다.

## 5. 항목의 상태 전이

```
                    ┌──────────── 결정론적 스윕 ────────────┐
                    ▼                                       │
   [감지됨] ──배정──▶ [대기] ──열림──▶ [열림]                 │
       │                                 │                   │
       │                    ┌────────────┼────────────┐      │
       │                    ▼            ▼            ▼      │
       │              [승인됨]      [수정됨]      [철회됨]    │
       │                    └────────────┴────────────┘      │
       │                                 │                   │
       │                                 ▼                   │
       │                            [해결됨] ──재감지──────────┘
       │                                                 (재발 배지)
       │              ┌──────────┐
       ├─────────────▶│ [보류]   │──깨어날 조건──▶ [대기]
       │              └──────────┘
       ▼
   [소멸] ← 사람이 손대기 전에 조건이 스스로 사라짐
```

| 상태 | 무엇 | 사용자에게 보이는가 |
|---|---|---|
| 감지됨 | 스윕이 만들었고 아직 세션에 안 들어옴 | 아니오 |
| 대기 | 오늘 세션 5개 안에 배정 | 접힌 줄로 |
| 열림 | 지금 펼쳐진 한 장 | 예 |
| 해결됨 | 승인·수정·철회 중 하나로 닫힘 | 2단계 활동 기록에 한 줄 |
| 보류 | 깨어날 조건을 들고 있음 | 아니오 (조건이 걸릴 때까지) |
| 소멸 | 근거가 되돌아왔거나 노트가 사라져 항목이 무의미해짐 | 2단계에 한 줄 — **조용히 지우지 않는다** |

**소멸을 기록으로 남기는 이유**는 신뢰 때문이다. 어제 본 항목이 오늘 아무 설명 없이 없어지면
사용자는 자기가 처리한 건지 시스템이 삼킨 건지 모른다. "9월 3일에 확인 요청했던 항목은
근거가 원래대로 돌아와서 없어졌어요" 한 줄이면 된다.

### 재발

해결된 항목이 **같은 identity**로 다시 감지되면 새 항목이 아니라 **재발**이다.
`signals.signal_hash`와 `(inference_id, note_id)` 쌍이 그 identity를 이미 들고 있다.

- 재발 항목은 자기 종류 안에서 맨 위로 올라간다.
- 카드에 `재발` 배지와 `n월 n일에 이렇게 고치셨어요` 한 줄이 붙는다.
- 세 번째 재발부터는 카드가 **개별 항목이 아니라 패턴**을 묻는다:
  "이 종류가 반복돼요. 규칙으로 만들까요?" → `rule-proposal`로 승격.

이것이 계약 §홈 우선순위 4번(`사용자가 이전에 교정한 내용과 같은 오류의 반복`)이
별도 목록이 아니라 배지로 존재하는 방식이다. 목록을 하나 더 만들면 큐가 둘이 된다.

## 6. 보류 — 시간이 아니라 조건

`나중에`가 단순 스누즈면 큐는 결국 부채가 된다. 보류는 **깨어날 조건**을 함께 저장한다.

| 종류 | 깨어날 조건 |
|---|---|
| `evidence-corrected` · `evidence-moved` | 그 노트가 다시 **주입**될 때 (`retrieval_log.injected`) 또는 근거가 또 움직일 때 |
| `belief-conflict` | 어느 한쪽이 다시 인용될 때 |
| `rule-proposal` | 같은 취지의 규칙이 또 제안될 때 |
| `evidence-missing` | 근거 파일이 다시 나타날 때 |

**보류한 기억이 실제로 AI에게 쓰이면 다시 올라온다.** 안 쓰이면 안 올라온다.
이것이 "전체 백로그를 부채처럼 상시 노출하지 않는다"를 지키면서도 위험한 것을 놓치지 않는 방법이다.

한 번도 주입된 적 없는 항목이 보류 상태로 오래 남는 것은 문제가 아니다. 아무도 그 기억을
쓰고 있지 않다는 뜻이기 때문이다.

## 7. 두 번째 위계 — 검토가 아닌 변경 기록

1단계와 섞이지 않도록 **다른 것만** 담는다.

들어오는 것:
- 현재 믿음의 값이 바뀐 것 (register 이벤트, state 노트 갱신) — 이전 값 · 현재 값 · 출처 세션
- 1단계에서 사람이 방금 처리한 것들의 결과 한 줄
- 소멸한 항목 한 줄

들어오지 않는 것:
- `노트가 추가됨` (믿음이 안 바뀐 저장은 접는다)
- 폴더·파일 경로별 그룹핑
- 볼트 정리 항목

> Opula의 LLM 공급자가 Groq에서 Vercel AI Gateway로 바뀌었어요 · 9월 4일 세션 · ▸ 이전 값 보기

여기에는 **버튼이 없다.** 판단이 필요하면 그건 1단계 항목이었어야 한다.

## 8. 신뢰 보정 — 무엇을 어떻게 말하는가

사용자가 이 앱을 믿어야 하는 정도는 항목마다 다르다. 그 차이를 화면이 말해야 한다.

### 출처 등급

| 등급 | 무엇 | 문구 | 1단계에 오는가 |
|---|---|---|---|
| **관측** | 기계가 확인한 것 — 해시 불일치, `invalidates` 링크, 파일 없음 | 단정. "9월 2일 정정됐어요" | 예 |
| **추론** | LLM이 합성한 것 — inference 요약, 충돌 후보의 해석 | 출처 명시. "AI가 이렇게 정리했어요" + 원문 발췌 병기 | 예 (원문과 함께일 때만) |
| **추측** | 임계값 휴리스틱 — `stale_state`, 근접도 | 홈에 오지 않는다 | 아니오 |

계약의 "AI가 생성한 요약과 원문 관찰을 구분한다"가 이 표다. 카드 우상단의 작은 라벨 하나면 된다.

### 문구 규칙

- **승인의 비용도 말한다.** 승인은 무료가 아니다. `맞아요`를 누르면 AI가 그 값을 더 강하게 쓴다.
  근거 패널에 `승인하면: 이 주장이 확인된 것으로 표시되고 다음 대화에 그대로 쓰여요`.
- **모르면 결론을 만들지 않는다.** `evidence-missing`은 "아마 이 노트였을 거예요"라고 쓰지 않는다.
  `근거를 읽지 못했어요 — 파일이 옮겨졌거나 지워졌을 수 있어요`가 정확한 문장이다.
- **보편적 헤지 금지.** 모든 카드에 "확인해 보세요"를 붙이면 신호가 죽는다.
  관측 등급은 단정하고, 불확실한 것만 불확실하다고 쓴다.
- **금지어**: `AI가 확신해요`, `중요한`, `위험한` 같은 형용사로 위계를 만드는 것.
  위계는 재발 여부와 주입 횟수라는 사실로 만든다.

### 금지하는 연출

- 볼드·색·배지로 확신을 연출하는 것. 추론 등급 카드가 관측 등급 카드보다 강해 보이면 안 된다.
- 코퍼스 전체에서 줄지 않는 카운터를 진행률로 쓰는 것. 진행률은 **세션 단위 `2 / 5`** 뿐이다.
- 남은 항목 수를 상시 배지로 노출하는 것.

## 9. 세션 규율

- 한 세션 **5개**. 위험도 순으로 뽑고, 나머지는 오늘의 몫이 아니다.
  (`today.ts`의 `DAILY = 9`는 정리 항목과 섞여 있을 때의 숫자다. 검토만 남으면 5가 맞다.)
- 우선순위는 계약 §홈 화면 계약의 목록을 따른다:
  `rule-proposal` → `belief-conflict` → `evidence-corrected` · `evidence-moved` · `evidence-missing`.
  **재발은 별도 순위가 아니라 자기 종류 안에서의 승급이다.**
  같은 종류 안에서는 최근 주입 횟수가 많은 것이 먼저다.
- 라운드로빈은 쓰지 않는다. 종류를 섞어 배정하던 이유가 "정리 항목이 큐를 다 먹는 것"이었는데
  정리 항목이 빠지면 그 이유가 사라진다.

### 빈 상태 (계약 지정 문구 유지)

```
지금 확인할 것은 없어요
지난 확인 이후 기억은 추가됐지만 현재 믿음과 행동 규칙은 안전하게 유지되고 있어요.
```

### 오류 / 근거 부족

```
이 항목은 근거를 읽지 못했어요
파일이 옮겨졌거나 지워졌을 수 있어요.
[ 원본 위치 보기 ]   [ 나중에 ]
```

승인 버튼이 없는 것이 이 상태의 핵심이다.

## 10. 아직 재료가 없는 것

정직하게 미결로 남긴다. 없는 것을 있는 것처럼 설계하지 않는다.

| 필요한 것 | 지금 상태 |
|---|---|
| 보류의 깨어날 조건 저장소 | 없다. `signals.status='snoozed'`는 조건을 안 들고 있다 |
| 재발 판정 | `signal_hash`는 있지만 "해결됨" 이력이 없다. 항목 처분 기록이 필요하다 |
| state 노트의 이전/현재 값 | git에는 있고 DB에는 없다. `history.ts`가 읽는 경로를 쓴다 |
| `belief-conflict` 실물 | 오늘 볼트에 0건. 가짜 데이터로만 검증 가능 |
| `rule-proposal` 실물 | 오늘 0건. #2283·#2284가 대기 중이나 아직 안 들어옴 |

**미검증 가설**: 사람이 이 큐를 실제로 소비할지, 다섯 개짜리 세션이 "끝냈다"는 감각을 주는지.
근거는 로그뿐이고 (앱은 전체 읽기의 0.36%, 하루만 열림), 그 로그는 검토 큐가 없던 시절 것이다.

## 11. 승인이 필요한 것

1. **§1의 두 게이트** — 그리고 그 결과로 오타 링크 128건·출처 미선언 30건·`stale_state` 30건이
   1단계에서 빠지는 것
2. **§4의 삭제 의미론** — 삭제를 종류마다 다른 것(거절·철회·아카이브)으로 쓰고,
   `past`는 삭제 대상에서 빼고, 부차 위치에 두는 것
3. **§4의 "근거 없으면 승인 버튼 없음"**
4. **§5의 재발을 별도 목록이 아니라 배지 + 세 번째부터 규칙 승격으로 처리하는 것**
5. **§6의 보류 = 조건부**, 특히 `retrieval_log.injected`를 깨어날 조건으로 쓰는 것
6. **§8의 출처 3등급**과 추측 등급을 홈에서 제외하는 것
7. **세션 크기 9 → 5**

승인되면 세로 조각 하나(`evidence-corrected` + `evidence-moved`, 오늘 13건)부터 만든다.
기존 사이드바·탭·헤더·라우팅은 건드리지 않고 홈 라우트의 내용만 바꾼다.
