# memex는 AI의 해마다 — 누구를 위한 것인가

> `2026-08-27-three-engine-second-brain.md`가 **무엇을 만들 것인가**를 정했고
> `2026-08-27-what-the-screen-answers.md`가 **화면이 무슨 질문에 답하는가**를 정했다.
> 이 문서는 **누가 쓰는가**를 정한다. 그 답이 앞의 둘에서 내린 결정 셋을 뒤집는다.

## 0. 확정된 넷

1. **memex는 AI가 사용하는 노트 툴이다.** 사람이 적는 것을 전제하지 않는다. `rule`도 에이전트가 쓰는 쪽으로 피벗한다
2. **초점은 AI가 기억을 추적·연결해서** 히스토리와 현재 상태를 파악하고 새로운 인사이트를 만드는 것이다
3. **데스크탑 앱은 두 가지를 위한 것이다** — memex(AI의 해마)가 어떻게 구성되어 있는지 보는 것, 그리고 AI가 잘못 기억한 것을 바로잡는 것
4. **앱 설치 → MCP 설치**로 연결된다. **비개발자를 위한 툴이다**

## 1. 쓰기의 주체가 갈렸다 — 사람은 새 기억을 만들지 않는다

1번과 3번은 충돌처럼 보인다. 하나는 사람이 안 쓴다고 하고 하나는 사람이 고친다고 한다.
충돌이 아니라 **역할 분리다.**

| | 쓰는 주체 | 무엇을 |
|---|---|---|
| 기억 생성 | **AI** | 새 기억 전부 (`past` · `state` · `rule`) |
| 기억 교정 | **사람** | AI가 틀리게 기억한 것만 |

"사람 전용 쓰기"가 사라지는 것이 아니라 **정당한 이유가 하나로 줄어든다.**
사람이 쓰는 유일한 이유는 **"AI가 틀렸다"**가 된다.

### 이것이 폐기된 정의와 어떻게 다른가

`2026-08-21-ui-roles.md`는 UI를 *"Claude가 대신 못 해주는 일"*로 정의했고,
`what-the-screen-answers`가 **그 기준이 UI에 잔반을 배정했다**며 폐기했다.
3번은 그 정의로 돌아가는 것처럼 보인다. 아니다.

**AI는 자기가 틀렸다는 것을 원리적으로 알 수 없다.** 능력 부족이 아니라 정보 접근 불가다.
"이 기억이 사실과 다르다"는 판정은 볼트 밖에만 존재한다.

> UI는 Claude가 못 하는 일을 하는 곳이 아니라,
> **Claude가 닿을 수 없는 정보의 유일한 입구다.**

`what-the-screen-answers`의 "화면은 다른 형태의 질문에 답한다"는 그대로 살아 있다.
교정은 그 질문(**무엇이 지금 참인가**)에 사람이 답을 정정하는 행위이지, 별도의 잡일 축이 아니다.

## 2. `rule` — 제안은 AI가, 승인은 사람이

1번에는 다른 layer에 없는 위험이 하나 있다. **`rule`은 자기 자신의 입력이 된다.**

```
에이전트가 rule을 쓴다 → 다음 세션에 주입된다 → 그 규칙대로 행동한다 → 또 rule을 쓴다
```

`three-engine` §1이 비목표로 **"자동 의미 병합 — 계산은 의미를 합성하지 않는다"**를 걸었고
§4가 자유 형식 fold를 *model collapse 경로*라며 거부했다. rule 자동 주입은 정확히 그 경로다.

### 결정 — `provisional` / `canonical`

```
save_note(layer=rule)  →  provisional 로 저장. 주입되지 않는다
앱에서 사람이 승인     →  canonical. 이후 주입된다
```

**AI는 rule을 쓸 수 있고, 자기가 쓴 것을 바로 읽지는 못한다.** 루프가 사람을 한 번 통과한다.
이것은 3번(사람이 교정)과 같은 메커니즘이며, 세 layer 중 `rule`만 승인을 요구한다.

### 부수 효과 — rule 예산 문제가 저절로 사라진다

지금 `rule` 12개 중 6개만 주입되고 나머지는 예산(10,000자)에서 잘린다.
잘리는 6개는 전부 **행동 규칙이 아닌 것**(작업지시서·백로그·사업 전략)이다.

`provisional`이 기본값이면 이 상황이 애초에 생기지 않는다. 사람이 승인한 것만 주입되고,
승인한 것은 정의상 행동 규칙이기 때문이다. **재분류는 일회성 정리로 끝나고 재발하지 않는다.**

## 3. CLI는 개발자용으로 밀어둔다

CLI 명령이 지금 **28개**다. 현재 정책은 *"MCP-first. The CLI is the safety net."*인데
safety net이 28개면 그것은 safety net이 아니다. 4번이면 그중 대부분은 **쓸 사람이 없다.**

| | 경로 |
|---|---|
| **비개발자** (주 대상) | 앱 설치 → **앱이 MCP를 등록** → 대화 + 앱 |
| **개발자** | 위 + CLI 28개 (진단 · 복구 · 자동화) |

**결정:** CLI를 지금 줄이지 않는다. 대신 **더 키우지 않는다.**
새 기능은 앱과 MCP에만 들어간다. surface policy의 "CLI는 safety net"을
**"CLI는 개발자용 진단·복구 도구"**로 다시 쓴다.

앱이 무엇을 흡수할지는 앱 설계가 구체화된 다음에 정한다. 그전에 CLI를 건드리는 것은 이르다.

### `memex mcp`가 성립하지 않는다

비개발자는 그 명령을 칠 수 없다. **앱이 MCP 설정을 써야 한다.**
지금 `apps/cli/src/commands/mcp.ts`에 있는 로직이 앱으로 가거나, 앱이 그것을 호출해야 한다.

## 4. Electron의 명분이 바뀌었다

`what-the-screen-answers`가 명분 셋을 세웠고 "읽기의 일상성이 제일 크고 유일하게 미측정"이라 했다.
4번이 그보다 큰 것을 얹는다.

| 명분 | 성격 |
|---|---|
| 존재(아이콘) · 알림(월 3~4건) · 읽기의 일상성 | **있으면 좋은** 이유 |
| **설치 경로** | **없으면 제품이 존재하지 않는** 이유 |

비개발자에게 앱은 UI가 아니라 **제품 그 자체다.** 앱이 없으면 memex에 도달할 방법이 없다.

## 5. §11 7번(register)이 부차에서 중심으로

착수 전 논의에서 "register는 읽기 중심 방향과 다른 축"이라고 판단했다. **그 판단이 틀렸다.**

| 컨셉 | register에서 무엇인가 |
|---|---|
| 2번 — 히스토리와 현재 상태 파악 | `(subject, predicate, scope)` register의 **정의 그 자체** |
| 3번 — 해마가 어떻게 구성됐는지 | register 키 목록과 각 tip이 **곧 그 화면** |
| 3번 — 잘못된 기억 교정 | **tip이 틀렸다고 사람이 말하는 것** |

**7번과 화면은 같은 것의 앞뒤였다.** 따로 논의할 것이 아니었다.

MCP 툴 표면 정책과도 실은 부딪히지 않는다. "13개로 작게 유지"의 근거는
*"duplicate read paths give the model more ways to pick wrong"* — **읽기 경로** 이야기다.
`set_register`는 새 읽기 경로가 아니라 새 쓰기 종류이고,
4번 때문에 **MCP가 유일한 쓰기 경로**가 된다.

## 6. 남은 질문

이 문서가 답하지 않는 것들. 앱 설계에서 정한다.

- **교정의 단위는 무엇인가** — 노트 본문인가, register tip인가, predicate 병합인가. 셋 다라면 화면이 셋이다
- **`provisional` rule을 사람이 언제 보는가** — `what-the-screen-answers`가 "끝나는 하루치 세션, 상시 백로그 카운터 금지"를 정했다. rule 승인도 그 규율을 따라야 한다
- ~~**앱이 MCP를 어떻게 등록하는가**~~ — **답했다.** 앱의 `연결` 화면이 클라이언트마다 자기 설정 파일을
  직접 쓴다(Claude·Claude Code·Codex·Cursor / JSON 셋 + TOML 하나). `mcp.ts`가 하던
  `claude mcp add` 셸아웃은 걷어냈다 — **비개발자에게는 그 CLI도 없다**
- **비개발자에게 배포를 어떻게 하는가** — 지금은 모노레포 + `yarn build` + dist 심링크다

## 7. 착수 순서에 미치는 영향

`three-engine` §11의 2~9번은 끝났다. 남은 7번의 성격이 바뀌었다.

1. **7번 register** — 이제 앱의 주 컨텐츠이므로, 스키마만이 아니라 **화면과 함께** 설계한다
2. **rule `provisional`/`canonical`** — 작고 독립적이며 1번 피벗의 전제다. 7번보다 먼저 할 수 있다
3. ~~**앱이 MCP를 등록**~~ — 4번의 전제. **끝났다**(`연결` 화면 + `mcp install` 재작성).
   남은 것은 앱 자체의 배포 경로다

`rule` 6개 재분류는 2번이 들어오면 일회성 정리로 흡수된다.
