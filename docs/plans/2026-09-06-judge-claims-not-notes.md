# 주장 레이어: 노트가 아니라 주장을 판정한다

> 운영 계약 memex #2280 §3 승인 요청서. 정보 구조와 상태가 먼저이고, 코드는 아직 손대지 않았다.
> 전제는 하나다. **노트는 원재료다. 사람이 판정할 수 있는 것은 노트가 아니라 그로부터 나온 주장이다.**
>
> 이 문서는 `2026-09-06-what-needs-your-judgement.md`를 폐기하지 않는다.
> 그 문서의 §1(두 게이트)과 §6(조건부 보류)은 그대로 살리고,
> §2(검토 항목 다섯 종류)의 **단위**를 노트에서 주장으로 바꾸자는 제안이다.

## 0. 먼저 확인한 것: 주장 레이어는 이미 있다. 진리 상태만 없다

`packages/db`의 스키마를 실측했다. (2026-09-06, `~/.memex/memex.db`)

| 테이블 | 행 수 | 상태 |
|---|---:|---|
| `note_claims` | **269** | 52개 노트에서 추출됨. 내용 품질은 좋다 |
| `register_events` | 4 | 전부 memex 자체 카운터 (`schema.version=13`, `tests=737`) |
| `register_subjects` | 1 | `memex` 하나뿐 |
| `register_predicates` | 4 | 전부 `provisional` |
| `inferences` | 9 | 전부 `stale` |
| `note_evidence` | 78 | |

`note_claims`의 실제 내용은 이미 원자적이고 판정 가능하다.

```
1767|1  awesome-mcp-servers는 오픈소스만 등록 가능해 opula(closed/hosted/paid)에는
        부적합하므로 스킵한다.
1767|2  PH 런칭 전 헌터와 초기 upvoter 10~20명 같은 첫시간 동원군이 없으면
        랭킹에 오르지 못한다.
```

**문제는 스키마다.**

```sql
note_claims(note_id INTEGER, idx INTEGER, text TEXT)
```

텍스트뿐이다. 참인지, 언제부터 참인지, 누가 확인했는지, 무엇이 이걸 대체했는지가 없다.
**판정할 수 있는 형태가 아니다.**

그런데 `register_events`에는 이미 답이 있다.

```sql
register_events(id, subject_id, predicate_id, scope, scope_start, scope_end,
                value, note_id, author, created_at)
```

`scope_start` / `scope_end`. **유효기간 스키마를 이미 설계해뒀고, 4건만 쓰고 있다.**
이 문서의 절반은 그 두 테이블을 합치자는 이야기다.

### 커버리지와 실사용

| | 실측 |
|---|---:|
| `state` 노트 | 254 |
| 주장이 추출된 노트 | 52 (20%) |
| 추출된 주장 | 269 |
| **AI에 실제로 주입된 적 있는 주장** | **77** (15개 노트) |

마지막 줄이 이 문서에서 가장 중요한 숫자다. 감독 대상은 1,382개 노트도, 269개 주장도 아니다.
**AI가 실제로 입 밖에 낸 77개**다.

## 1. 왜 노트가 아니라 주장인가

### 1-1. 노트는 판정 가능한 단위가 아니다

이메일에는 자연스러운 판정 단위가 있다. 한 통, 한 결정. PR도 그렇다. 머지하거나 안 하거나.

노트에는 그 경계가 없다. 노트 하나가 80% 맞을 수 있다.
"이 노트를 승인합니다"는 성립하는 질문이 아니다.

### 1-2. 외부 확인: 아무도 문서를 게이트하지 않는다

승인 게이트를 실제로 운영하는 제품 셋을 조사했다. 전부 같은 회피를 한다.

| 제품 | 게이트 단위 | 캡 |
|---|---|---|
| Seeq AI Assistant | 기억 한 줄 | pending 20 / approved 20 |
| Supermemory | 추론 한 건 | 큐 50 |
| Microsoft 365 Copilot | 사실 한 개 | 없음 |

세 제품 다 **원자적 주장으로 쪼갠 뒤에** 묻는다. 문서를 통째로 승인시키는 제품은 찾지 못했다.

반대편 사례도 명확하다. OpenAI는 사용자가 기억 목록을 직접 관리하는 모델을 시도했다가 폐기했고,
공식 FAQ에 이유를 적어뒀다.

> 이전 저장된 기억 시스템은 자주 낡았고 사용자가 직접 업데이트를 관리하는 데 의존했다.
> 기억들이 서로 모순될 수도 있었다.

그들의 해법은 사람을 더 넣는 것이 아니라 빼는 것이었다.
**memex가 사람을 남기려면 물어보는 단위가 달라야 한다.**

### 1-3. `past`는 영원히 참이고 `state`는 조용히 거짓이 된다

| 레이어 | 개수 | 성격 | 시간이 지나면 |
|---|---:|---|---|
| `past` | 880 | 역사 기록 | **절대 거짓이 되지 않는다** |
| `external` | 239 | 외부 자료 | 원문이 바뀌면 갱신 대상 |
| `state` | 254 | 현재 믿음 | **조용히 거짓이 된다** |
| `rule` | 9 | 행동 규칙 | 사람이 소유 |

"2026-08-16에 Vercel AI Gateway로 바꿨다"는 영원히 참이다. 역사는 거짓이 되지 않는다.
"Opula의 채팅은 Groq에서 gpt-oss-120b를 돌린다"는 8월 3일에 참이었고 8월 16일에 거짓이 됐다.

**`state`를 노트 포맷에 저장한 것이 근본 불일치다.**
가변 믿음을 불변 문서 형식에 넣었다. 그래서 갱신도 폐기도 판정도 안 된다.

이 전환은 실제로 세션 사이에 일어났고 memex는 잡지 못했다.
사용자가 "AI Gateway 사용량이 왜 비어 보이지"라고 물어서야 드러났다.

## 2. 주장의 최소 형태

`note_claims`에 상태를 붙인다. 필드는 `register_events`를 따른다.

```sql
note_claims(
  id           INTEGER PRIMARY KEY,   -- 신규. 참조·대체에 필요하다
  note_id      INTEGER,               -- 근거 노트
  idx          INTEGER,
  text         TEXT,

  valid_from   INTEGER,               -- 기본값: 근거 노트의 authored_at
  valid_until  INTEGER,               -- NULL이면 현재도 유효
  confirmed_at INTEGER,               -- 사람이 마지막으로 확인한 시각
  confirm_depth TEXT,                 -- 'card' | 'evidence'  (§7 참조)
  superseded_by INTEGER,              -- 이걸 대체한 주장의 id
  status       TEXT                   -- 'unconfirmed' | 'confirmed' | 'closed' | 'retracted'
)
```

**주장은 삭제되지 않는다.** 구간이 닫힐 뿐이다.
Zep/Graphiti의 bi-temporal 무효화와 같은 방식이다. 모순이 감지되면 지우지 않고 `t_invalid`를 세팅하고,
히스토리는 계속 조회 가능하게 둔다.

이유는 실무적이다. Groq 주장을 지우면 8월에 그 결정을 근거로 쓴 `past` 노트들이 근거를 잃는다.
"왜 바꿨나"를 물었을 때 이전 상태를 복원할 수도 없다.

## 3. 판정은 네 가지다. 이진값이 아니다

| 판정 | 무슨 일이 일어나나 | 예상 빈도 |
|---|---|---|
| **아직 맞아요** | `confirmed_at` 갱신, `status='confirmed'` | 가장 많다 |
| **바뀌었어요** + 새 값 | 기존 주장 `valid_until=오늘`, `status='closed'`, 새 주장 생성 후 `superseded_by` 연결 | **이 제품의 존재 이유** |
| **원래 틀렸어요** | `valid_from`부터 무효, `status='retracted'` | 드물다. 추출 오류인 경우 |
| **나중에** | 보류. 시간 또는 새 근거 중 먼저 오는 쪽에 복귀 | |

가장 흔한 실패는 "거짓"이 아니라 **"그때는 참이었는데 지금은 아님"**이다.
그래서 참/거짓 두 개로는 부족하고, 두 번째 항목이 핵심 경로다.

사람이 유일하게 갖고 있는 정보는 "틀렸다"가 아니라 **"지금은 이거다"**라는 값이다.
그 값을 받을 자리가 없는 설계는 이 제품을 성립시키지 못한다.

## 4. 확인이 절반이다

지금 검토 큐는 **나쁜 소식만 가져온다.** 뭔가 틀렸을 때만 사람을 부른다.

확인 흐름을 넣어야 하는 이유는 셋이다.

- **압도적으로 싸다.** 읽고 "응 맞아" 한 번이다. 정정보다 10배 싸고, 그래서 실제로 일어난다.
- **신선도를 만든다.** 확인 기록이 없으면 269개 주장이 전부 동등하게 의심스럽다.
  우선순위를 매길 근거 자체가 없다.
- **기각만 있는 큐는 기각을 학습시킨다.** 임상·보안 관제 연구에서 반복 확인된 결과다.
  볼륨을 98% 줄여도(245,757건 → 4,461건) 무시율은 96%로 유지됐다.
  **개수를 줄이는 것만으로는 신뢰가 회복되지 않는다.**

memex의 현재 `conflict_candidate` 기각률은 **65%(20건 중 13건)**다.
보안 관제 튜닝 기준(오탐 50% 초과 신호는 비활성화 또는 재정의)을 이미 넘었다.
확인을 기본 행동으로 만들면 큐의 의미가 "문제 목록"에서 "믿음 점검"으로 바뀐다.

## 5. 무엇을 물을지: 세 조건의 교집합

`what-needs-your-judgement.md` §1의 두 게이트에 **조건 하나를 앞에 붙인다.**

| 게이트 | 질문 | 아니면 |
|---|---|---|
| **① 영향 (신규)** | AI가 이 주장을 실제로 말한 적 있는가 | 묻지 않는다 |
| **② 의심** | 신선도가 만료됐거나, 근거가 바뀌었거나, 모순 후보인가 | 조용히 둔다 |
| **③ 답변 가능** | 사람만 답할 수 있고, 결정론적으로 근거를 댈 수 있는가 | 3단계 볼트 정리 |

①이 결정적이다. **한 번도 주입된 적 없는 주장은 물어볼 가치가 없다.**

지금 큐가 65% 기각당하는 이유는 항목이 "그래서 뭐"이기 때문이다.
카드 맨 위에 **"AI가 지난 30일 동안 이 말을 3번 했어요"**가 붙으면 답할 이유가 생긴다.
이건 볼륨 감축이 아니라 질적 변화라서, 위에서 인용한 "98% 줄여도 96% 무시" 함정을 피한다.

### 실측 필터 통과량

```
전체 주장                      269
① 주입된 적 있음                77
  └ 100자 이하 (판정 가능)      62
② + 신선도 만료 (30일 기준)     한 자릿수 예상
```

`retrieval_log`는 지금 `note_id` 단위다. 주장 단위 로그가 없으므로
**1단계에서는 노트 단위 주입을 프록시로 쓴다.** "이 노트가 주입됐다"를 "이 노트의 주장들이 발화됐다"로 읽는다.
회수 코드를 건드리지 않고 오늘 계산 가능하다.

## 6. 카드 덱: 확인은 리듬, 정정은 이탈

주장 하나가 카드 하나다. 세션 단위로 비워진다.

```
        ┌────────────────────────────────────┐
        │                                    │
        │  Opula의 채팅은 Groq에서             │
        │  gpt-oss-120b를 돌린다               │
        │                                    │
        │  8월 3일부터 · 34일째 확인 안 됨      │
        │  지난 30일 동안 대화에서 3번 썼어요    │
        │                                    │
        │  근거  Opula 인앱 채팅 LLM 비용 비교 ▾ │
        └────────────────────────────────────┘

      ← 아직 맞아요            바뀌었어요 →
                  ↓ 나중에

                    3 / 7
```

### 좌우가 대칭이 아니다

여기가 이 설계의 핵심이고, 흔한 스와이프 UI와 갈라지는 지점이다.

| 방향 | 비용 | 필요한 입력 | 동작 |
|---|---|---|---|
| **← 확인** | 0 | 없음 | 다음 카드로. 리듬 유지 |
| **→ 정정** | 높음 | **새 값** | **덱이 멈추고 입력 모드로 전환** |
| **↓ 보류** | 0 | 없음 | 다음 카드로 |

**정정에서 리듬이 깨지는 것은 의도다.** 생각해야 하는 자리이기 때문이다.

정정을 스와이프로 만들면 이 제품에서 가장 값진 정보(새 값)를 버리게 된다.
`→`는 "틀렸으니 지운다"가 아니라 "구간을 닫고 다음 구간을 연다"이므로, 입력 없이는 완료될 수 없다.

### 단축키

| 키 | 동작 |
|---|---|
| `←` 또는 `1` | 아직 맞아요 |
| `→` 또는 `2` | 바뀌었어요 (입력 모드 진입) |
| `↓` 또는 `3` | 나중에 |
| `Space` | 근거 펼치기 / 접기 |
| `⌘Z` | 직전 판정 되돌리기 |

행동 수를 넷으로 묶는 것은 Linear Triage와 같다(수락/중복/거절/스누즈).
**되돌리기는 항상 노출하고 무료여야 한다.** 잘못 넘긴 카드가 AI 행동을 바꾸기 때문이다.

## 7. 확인을 정직하게 유지하는 장치

한 키 확인에는 조용한 위험이 있다.

`confirmed_at`이 "사람이 검증했다"를 뜻해야 하는데, 한 키로 끝나면 실제로는
**"사람이 키를 눌렀다"**를 뜻하게 된다. 그러면 §4에서 만든 신선도 신호 전체가 거짓이 된다.

이건 조사에서 안티패턴으로 뽑은 것과 같은 실패다.
ChatGPT의 기억 요약은 "여기 내가 아는 것, 틀린 걸 지우세요"처럼 보이지만
거기서 지워도 실제 믿음은 지워지지 않는다. **감독처럼 보이지만 감독이 아닌 목록**이 된다.

속도를 벌하지 않으면서 이걸 막는 방법은 **깊이에 따라 값을 다르게 매기는 것**이다.

| `confirm_depth` | 조건 | 신선도 연장 |
|---|---|---|
| `card` | 카드만 보고 확인 | **30일** |
| `evidence` | 근거를 펼치고 확인 | **90일** |

대충 확인한 주장은 더 빨리 다시 물어본다. 확인을 막지 않고 가격만 다르게 매긴다.

## 8. 게이미피케이션의 경계

리듬과 낮은 마찰은 가져오되, **처리량을 보상하지 않는다.**

Anki에서 게이미피케이션이 작동하는 이유는 정답이 존재하기 때문이다.
대충 하면 자기가 손해를 본다. 여기서는 사람이 곧 정답이라 교정 신호가 없다.
카드 수나 점수를 보상하면 정확도가 아니라 속도에 최적화된다.

### 넣는 것

- **빈 상태 자체.** 세션을 끝냈다는 감각은 완료 화면으로 준다.
- **확인된 비율.** "AI가 아는 것 중 확인된 것 N%". 대충 넘기면 30일 뒤에 도로 내려간다.
- **세션 단위 진행률 `3 / 7`.** 계약 §진행률 규정 그대로다.

### 넣지 않는 것

- **연속 기록(스트릭).** §9의 소프트 게이트 원칙과 정면 충돌한다.
  스트릭은 부재를 처벌하는데, 이 큐는 무시해도 괜찮아야 한다.
- **점수·레벨·배지.**
- **남은 항목 수 상시 배지.** 상시 카운터는 회피를 학습시킨다.
  0일 때와 아주 클 때는 숨긴다.

## 9. 판정이 AI 행동을 바꾸는 경로

이게 없으면 판정이 무의미하고, 무의미하면 기각이 기본값이 된다.

| 주장 상태 | 회수될 때 |
|---|---|
| `confirmed` | 우선 주입 + "9월 6일 확인" 표시 |
| `unconfirmed` | **주입되되 가중치 하락** |
| `closed` | 새 주장이 주입. 옛 값은 "8/3~8/16 참이었음"으로만 조회 |
| `rule` 승격 | 항상 주입 |

Supermemory의 소프트 게이트와 같은 구조다.
그들은 시스템이 **추론한** 사실만 큐에 넣고(`isInference: true`), 미검토 상태에서도 검색에는 걸리되
가중치를 낮춘다. **검토하지 않는 것이 실패가 아니라 비용이다.**

이 성질이 중요한 이유는, 큐를 몇 주 방치해도 제품이 망가지지 않기 때문이다.
방치하면 회수 품질이 서서히 떨어질 뿐이고, 그건 사용자가 스스로 느낀다.

## 10. 회수 쪽 변화

주입 단위를 노트 전문에서 주장으로 바꾸면 셋이 따라온다.

- **컨텍스트가 준다.** 노트 전문 대신 문장 몇 개.
- **시점을 붙일 수 있다.** "2026-08-03 기준"을 같이 넣으면 모델이 알아서 할인한다.
- **`stale_state` 36건이 큐에서 사라진다.** 그 신호는 "무엇이 어떻게 틀렸는지" 말하지 못해서
  사람이 판정할 수 없는 항목이었다. 타임스탬프로 넘기면 된다.

> 재검증은 토큰이 들지만 타임스탬프는 들지 않는다.

## 11. 이 문서가 결정하지 않는 것

- **폴더/`Overview.tsx`의 그룹화 축.** 별도 결정이다. (실측: 126개 카테고리 중 `projects` 750 + `work` 258 = 73%)
- **검색.** `2026-09-06-search-for-people-who-forgot-the-word.md`가 담당한다.
  다만 그 문서의 "무엇이 일치했는지" 복구는 이 문서의 근거 표시와 재료가 같다.
- **시각 언어(타이포그래피·깊이·강조색).** 이 결정 다음에 온다.
  단, 카드 덱이 채택되면 "한 주장만 크게" 방향이 자연스럽게 따라온다.
- **앱 셸.** 사이드바·탭·헤더·라우팅은 건드리지 않는다. #2280이 명시적 승인 없는 재구조화를 금지한다.

## 12. 아직 재료가 없는 것

정직하게 미결로 남긴다.

| 필요한 것 | 지금 상태 |
|---|---|
| 주장 단위 `retrieval_log` | 없다. 노트 단위 주입을 프록시로 쓴다 (§5) |
| 확인 이력 테이블 | 없다. `confirmed_at` 한 칸으로 시작하고 이력은 나중에 |
| 주장 추출 커버리지 | **20%** (254개 중 52개). 나머지는 추출 안 됨 |
| 주장의 원자성 | **40건이 100자 초과.** 아래 참조 |
| `superseded_by` 체인 UI | 미설계. 1단계에서는 저장만 하고 보여주지 않는다 |

### 원자성 미달은 실제 문제다

길이 분포 실측: 40자 미만 10건, 40~69자 120건, 70~99자 99건, **100자 이상 40건**.

100자 이상 예시:

```
커플은 임대+주식 노선으로 40대 중후반(허리띠나 와이프 사업 가속 시 40대 초반)에
FIRE(약 25억)를 달성할 수 있다.
```

노선, 시기, 조건, 금액이 한 문장에 섞여 있다. **참/거짓 판정이 불가능하다.**
추출 프롬프트에 원자성 제약을 넣거나, 카드에 "쪼개기" 행동을 추가해야 한다.
1단계에서는 100자 초과 주장을 큐에서 제외하는 것으로 우회한다.

### 추출도 LLM이 한다는 재귀 문제

주장 추출 자체가 LLM 작업이므로 검증 문제가 한 겹 더 생긴다.

완화 논리는 §5의 게이트 ①이다. **주입된 주장만 검토 대상**이므로,
추출 오류는 그 주장이 실제로 쓰인 순간에만 문제가 된다.
쓰이지 않는 주장의 추출 품질은 사용자에게 영향을 주지 않는다.

### 미검증 가설

사람이 이 덱을 실제로 소비할지는 아직 모른다.
근거가 될 로그는 검토 큐가 없던 시절의 것이고, 앱은 전체 읽기의 극소수다.
콜드 스타트(269개 중 확인 0개)를 한 번 통과시켜 보는 것이 첫 검증이다.

## 13. 승인이 필요한 것

1. **판정 단위를 노트에서 주장으로 바꾸는 것** (§1). 검토 카드의 주어가 노트 제목이 아니라 주장 문장이 된다.
2. **`note_claims`에 유효기간·확인·대체 필드를 추가하는 것** (§2). `register_events` 스키마를 따른다.
3. **주장은 삭제하지 않고 구간을 닫는 것** (§2, §3). `closed`와 `retracted`를 구분한다.
4. **게이트 ① 추가**: 주입된 적 없는 주장은 큐에 넣지 않는다 (§5).
   결과로 `stale_state` 36건과 `dangling_link` 129건(미처리 기준, 누적 168건)이
   1단계에서 완전히 빠진다.
5. **확인을 1급 행동으로 만드는 것** (§4). 지금은 정정 계열만 있다.
6. **카드 덱의 비대칭** (§6): 확인은 스와이프, 정정은 입력 모드 진입.
7. **`confirm_depth`에 따른 신선도 차등** 30일 / 90일 (§7).
8. **스트릭·점수·상시 배지를 넣지 않는 것** (§8).
9. **미검토 주장도 주입하되 가중치를 낮추는 것** (§9). 큐 방치가 제품을 망가뜨리지 않게 한다.

승인되면 세로 조각 하나부터 만든다.

**1차 범위**: `note_claims` 스키마 확장 + 노트 단위 주입 프록시 + 확인/보류 두 행동만.
정정(입력 모드)과 `superseded_by` 체인은 2차로 미룬다.
대상은 오늘 실측 기준 **62개**다.
(주입된 적 있는 주장 77개 중 100자 이하인 것. 여기에 신선도 만료 조건이 붙으면 한 자릿수로 떨어진다.)

기존 사이드바·탭·헤더·라우팅은 건드리지 않고 홈 라우트의 1단 내용만 바꾼다.
